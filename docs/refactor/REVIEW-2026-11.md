## 1. Confirmed defects

### D1 — Upgrading a database initialized before PR #50 fails (High, reproduced) **[F1]**

**Where.** `core/mem-gecko/schema/mem_types.tql:252` (the `population-member` `@doc` text was
edited in PR #50); `core/gecko-engine/src/db/router.rs:240-272` and
`core/gecko-engine/src/db/schema_apply.rs:90-120` (only functions get `redefine`).

**Failure scenario.** Take any database whose mem schema was applied before PR #50 and run
`gecko schema-init` or `gecko sync` (both call `apply_all_schemas`,
`gecko-bin/src/main.rs:602`). The mem fragment's `define` is rejected:

```text
[DEX15] Defining annotation '@doc("… over the window it held and with a staleness marker.")'
for type 'population-member' failed since a different 'population-member @doc("… with a
staleness marker.")' is already defined. Try redefine instead?
```

TypeDB's `define` is idempotent only for *identical* type definitions; a changed annotation
(`@doc` here, and by the same rule `@card`/`@values`) is refused exactly as a changed function
is. The re-appliable schema path fixed `[FUN5]` for functions and left the equivalent type
case open, and the same PR then shipped a type-annotation change. The ledger's claims that
rows #3/#4/#9 "reach already-initialized DBs via #11" are therefore false for the one upgrade
that actually exists.

Reproduction: pre-#50 schema (`git show 95ebac1:core/mem-gecko/schema/*.tql`) applied to a
fresh database, then the shipped mem schema applied over it. With the single `@doc` string
pre-aligned, the same upgrade succeeds — including the `blast-radius` param widening, the
`population-members` body change and the three new functions — so the function half of #11
does work; the type half is the whole failure.

**Why the tests missed it.** `schema_migration_test.rs` re-applies the *same* schema and
mutates one *function body*. Nothing applies the previous release's schema and then the
current one.

**Secondary effect.** `apply_all_schemas` commits one schema transaction per fragment, so the
failed upgrade leaves the core fragment applied and the mem fragment not — re-runnable, but
not atomic across fragments.

**Suggested fix.**
1. Immediate: an explicit migration step. Verified live — a fragment
   `redefine relation population-member @doc("<new text>");` applied first makes the
   subsequent `schema-init` succeed.
2. Structural: give schema application an ordered, versioned migration list (explicit
   `redefine`/`undefine` fragments keyed by a schema-version marker stored in the database)
   that runs before the idempotent `define`. Drop-and-recreate is not an acceptable default
   here: the belief tier is a system of record, not rebuildable from the bundle.
3. Test: pin the previous release's composed schema as a fixture and assert
   `apply(previous) → apply(current)` succeeds; run it in the per-push TypeDB job.
4. Correct the doc comments that state types are re-applied idempotently
   (`router.rs:233-239`, `main.rs:598-601`).

### D2 — Function redefinition is order-dependent (Medium, reproduced) **[F2]**

**Where.** `schema_apply.rs:98-118` — one `define` (types + new functions) is sent first, then
one `redefine` per existing function in source order.

**Failure scenario.** Functions `a` and `b` both exist; a release changes `a`'s signature and
updates its caller `b`. If `b` precedes `a` in the fragment, `redefine b` is validated against
the *stored* `a` and fails:

```text
[REP3] Invalid call to function 'rv-a', which requires '1' arguments but only '2' were provided.
[REX38] Redefining the function 'rv-b' failed
```

With `a` first the same change applies cleanly. Putting both in a single `redefine` block does
not help (also reproduced) — TypeDB validates each function as it is redefined. The same
ordering problem applies to a *new* function (sent in the leading `define`) that calls an
existing function with its new signature.

The shipped schema does not trip this today (`blast-radius`'s only caller is itself, and the
widening is backward-compatible). It is a latent limit of the mechanism the ledger records as
complete.

**Suggested fix.** Order statements by call dependency (callee first) across both the
`redefine` set and the new-function `define`s: scan each body for names in the fragment's
function set, topologically sort, and send new functions in their own `define` at the right
point. A simultaneous signature change in mutually recursive functions cannot be expressed
this way; detect it and return a `DbError::Schema` that says so rather than surfacing `[REP3]`.

### D3 — A statement after a function applies once, then breaks every re-apply (Medium, reproduced) **[F2]**

**Where.** `schema_apply.rs:19-21, 57-65`. The "type after function" guard only recognizes
lines that begin with `entity|relation|attribute|struct`.

**Failure scenario.** A fragment contains an additive statement after its last function —
`concept owns zz-test @card(0..1);`, or the `<type> plays <role>;` form that
`mem_types.tql:283-286, 317-325` already uses. On a fresh database the fragment is passed
through unchanged and applies. On the next `schema-init`/`sync` the statement is carried
inside the preceding function's `redefine` text and TypeDB rejects it:

```text
[REX27] Redefining annotation '@card(0..1)' for a capability failed since is already defined identically.
```

So the database initializes and then refuses every later sync. The shipped fragments keep all
type statements ahead of all functions, so nothing is broken today; the exposure is the
`--schema` custom file and any future extension fragment.

**Suggested fix.** Terminate a function block structurally instead of by keyword: a function
ends at the `return …;` statement, so any following non-blank, non-comment line that is not
`fun` belongs to the type section — reject it with the existing error (or route it to the
`define` body). That also stops trailing comments being attached to the previous function.
Longer term, replace the line/regex splitter with a small statement-level tokenizer; the
current one also assumes `define` sits alone on its line and `fun name(` on one line.

### D4 — Populations writer reads and writes in separate transactions (Medium, by reading) **[F3]**

**Where.** `core/mem-gecko/src/writer.rs:447-464` (`materialize_population`), `:470-494`
(`close_population_membership`), `:403-437` (`define_population`). `GraphStore::read` opens
its own read transaction (`graph_store.rs:107`); the single-writer gate
(`router.rs:366-382`) serializes writes only, and only within one process.

**Failure scenarios.**
- *Duplicate open rows.* Two passes for the same population overlap. Both read "no open row
  for `a`", both plan `open: [a]`, and the gate lets the two inserts commit one after the
  other. `a` now has two open epoch rows. `population_members` hides it (host-side dedup),
  but `rows`/epoch counts are wrong and a later pass reports `closed: 1` while closing two.
- *Stale-pass guard bypass.* Pass A (`at = t2`) and pass B (`at = t1 < t2`) overlap. Both
  read rows last stamped `t0`, both pass the `at < latest` check
  (`populations.rs:83-94`), and B's `update … has computed-at == $at` commits after A's —
  `computed-at` moves backwards and a window can close at `t1` beside a row opened at `t2`.
- *Zero-row opens.* `require_concepts` runs in its own read; a member removed before the
  write makes `open_membership_op` match nothing, and the pass still reports it as opened.
- *`define_population` race.* Two callers both see "absent"; the second insert fails on the
  `spec-hash` key and surfaces as `EpistemicError::Storage` instead of `Ok(false)`.

The module doc states the opposite of what the code does: "reads the rows, calls it, and
applies the result in one transaction" (`populations.rs:14-15`). Only the three write ops
share a transaction.

There is no production caller yet, so nothing is corrupted today; the first caller will be
the consolidation daemon or a spec evaluator, both of which run concurrently with sandbox
writes.

**Suggested fix.** Make the write ops self-guarding so correctness does not depend on the
earlier read: the open op carries `not { <an open row for this member exists> }`; close and
refresh carry the stale guard as a match condition (`not { $pm has computed-at $ca; $ca > $at; }`).
Add a per-population async lock in `MemWriter` for the read-plan-write sequence within a
process. If more planners of this shape are coming (the daemon's jobs are), add a
read-your-writes transaction to `GraphStore` instead of repeating the pattern.

### D5 — Belief validity windows are never closed, so the as-of functions disagree with their specification (Medium, by reading; latent until a resolution writer exists) **[B1–B3]**

**Where.** `core/mem-gecko/src/tql.rs:277-304` (`supersession_ops` flips `belief-state` and
writes nothing else); no builder in `tql.rs` writes a belief's `valid-to`.
`core/mem-gecko/schema/mem_functions.tql:20-25` (`believed-at`), `:199-219`
(`canonical-entity-at`), and the comment at `:162-166`.

**Failure scenarios.**
- *`canonical-entity-at` keeps following dead resolutions.* It gates on the resolution's
  window only (by design, SPEC-W2-W3 §3.3). A provable resolution asserted at `t1` and
  superseded at `t2` as wrong has no `valid-to`, so `canonical-entity-at($rec, t)` merges the
  two records for every `t ≥ t1`, including now — while present-state `canonical-entity`
  correctly drops it. The acceptance test `canonical_entity_at_recursive_asof_closure`
  passes because its fixture hand-writes `valid-to`.
- *`believed-at` is not an as-of read.* It requires `belief-state "asserted"`, a present-state
  fact. A belief superseded today vanishes from `believed-at(t)` for every past `t` at which
  it was held. SPEC-W2-W3 §3.3 states the opposite ("mirroring how `believed-at` reads
  windows, not state"), and PR #50 copied that claim into the schema comment at
  `mem_functions.tql:162-166`. `believed_at_and_members_at_agree_as_of_t` passes because its
  fixture never supersedes anything, so the T5 composition the test is named for is only
  fixed for the population half.

**Suggested fix.** This needs a decision, not a patch (ledger **[D-A]**): either `supersede`
closes the superseded belief's `valid-to` at the supersession time and `believed-at` reads
the window instead of the state, or the as-of functions consult `supersession.created-at`.
Until it is decided, `canonical-entity-at` should not be consumed by a resolution writer, and
the comment at `mem_functions.tql:162-166` should stop asserting the mirror.

### D6 — Present-state `blast-radius` follows closed membership rows (Low–Medium, by reading; known) **[F4]**

**Where.** `mem_functions.tql:67-83` versus `population-members` at `:133-137`.

The inconsistency was left deliberately when present-state membership started excluding
closed rows. Two things changed that make it worth closing now: closed rows are no longer a
test artifact (the populations writer produces them on every departure), and
`blast-radius-at(now)` is not an equivalent substitute for callers that hold only the
`EpistemicReader` trait. A member that left a cohort still sweeps every belief scoped to it.

A related gap: `EpistemicReader::blast_radius` (`writer.rs:1110-1121`) binds
`$r isa memory-item`, so the widened `okf-concept` parameter is unreachable through the trait;
only the inherent `blast_radius_at` accepts a member concept.

**Suggested fix.** Add `not { $pm has valid-to $vt; }` to both population branches of
`blast-radius` (a body-only change, which the redefine path handles). Decide whether the trait
method should accept a `ConceptId` or the member entry point stays `blast_radius_at`-only, and
say which in the trait doc.

## 2. Judgment calls on what was built

**Disposition ranker — a human assertion without evidence ranks below an LLM synthesis.**
`derivation-method` is stored only on the `derivation` relation, and `derivation_op` writes
none when a belief has no evidence. `effective_method` then yields `None`, which sorts below
every real method (`disposition.rs:140-145`). A bare human assertion — the common shape — so
loses key #1 to an `llm-synthesis` belief that cites anything. The module documents the rule;
I think the outcome is wrong for §8.2's intent. The stored `entrenchment` already encodes the
method class and could be the fallback. Belongs in the contract for the disposition writer
**[A6]**.

**Ranker versus the entrenchment guard.** The ranker puts provable above attested; the
supersede guard puts `user-stated` (human) above `tool-derived` (provable). For an
instance-vs-instance divergence the ranker can pick a provable winner whose supersession of
the human-asserted loser the guard then refuses. SPEC-W2-W3 §2.4 covers a human *winning*;
nothing says what the writer does in the reverse case. Needs a decision before **[A6]**
(ledger **[D-C]**).

**`schema_apply` is a reasonable fix carrying more than its design supports.** The pure
planner with unit tests is the right shape, and fixing `[FUN5]` re-application was necessary.
But a regex line-splitter is now the gate for every schema fragment including user-supplied
`--schema` files, and "re-appliable" is being read as "migratable" (D1). I would name it what
it is — function-aware re-apply — and build migrations as the separate explicit mechanism in
D1's fix. Functions removed from the shipped schema are never undefined; that belongs in the
same migration list.

**Populations writer design.** Having the caller supply the evaluated member set and never
executing stored `spec-text` is the right call (no stored-query execution surface). The pure
planner is well tested. Three gaps beyond D4: the writer takes no `RunContext`, so a
population and its membership epochs have no run/actor attribution (CONTRACT-W8 CF-3's
per-tick reconciliation cannot cover them); a row written before windows existed is treated
as open but stays invisible to `population-members-at` (no `valid-from` backfill); and
`existing_concepts_read` builds one disjunct per member, which will not scale to large
cohorts (it is correctly parameterized — no injection risk).

**`MemWriter` size and inline TQL.** `writer.rs` is ~1,400 lines and PR #50 added a fourteenth
inline reader (`blast_radius_at`, `:549-561`) next to the comment deferring their
consolidation. The seam work will add more. Split before the seam lands, not after: readers,
populations, and the forthcoming edge writer as submodules, all query text in `tql.rs`.
**[F7]**

**Tests.** Coverage of the happy paths is good and the acceptance suite is green. Missing:
previous-release upgrade (D1), concurrency on the populations writer (D4), any fixture that
supersedes a belief before an as-of read (D5).

## 3. Architectural concerns about the seam ① plan (SPEC-W5 §3)

The registry design is sound in outline — general without being free-form. These are the
points I would settle before writing it; each is a ledger decision or a design input to **[A1]**.

1. **Nothing structural stops an extension registering a mem-owned relation.** §3.1 rejects
   a free-form `link_belief` because `supersession{…}` would bypass the entrenchment guard.
   A registry that accepts any *declared* relation reopens that hole one step removed: declare
   `supersession`, then write it. The protection in §3.2 is "registered, reviewed", which is
   procedural. The registry should refuse any relation defined by the core or mem fragments,
   so only extension-owned relations are declarable. **[D-B]**
2. **Mem-owned edges need dedicated writers, not declarations.** `scoped`, `resolves` and
   `divergence-precedence` each carry their own guard (co-mint, disposition, provable-only).
   §3.2's "the seam refuses an anchor-less `divergence-precedence`" is really a description of
   a dedicated `MemWriter` method. Treating those three as registry clients blurs the one
   distinction that makes the registry safe.
3. **Labels are interpolated, so the seam is an exception to "all TQL is parameterized".**
   Relation, role and attribute labels cannot be `given` parameters. The seam must validate
   every declared label against a strict identifier pattern at registration and against the
   live schema before first use, and the W5a static lint (which looks for literal type names)
   cannot see these writes — the dynamic half has to carry them.
4. **Belief and edge should commit together.** Cyber today writes the belief
   (`detect/mod.rs:120`) and the relation (`:142`) in two transactions; a failure between
   them leaves an orphan belief. A seam that only writes an edge to an existing belief keeps
   that split and leaves "a belief the current run is entitled to reference" undefined. Making
   the primary shape "assert a belief with its declared edges, one transaction" removes both
   problems and is the same shape the co-mint writer needs.
5. **Extensions still hold a write-capable handle.** After the cyber migration the bridge
   keeps `Arc<dyn GraphStore>` for reads (§3.3), which is also the raw write path. Splitting
   the trait and handing extensions a read-only half would retire the §2.1 residual
   structurally instead of by test. **[D-D]**
6. **Registration needs an API change.** `GeckoExtension` has no declaration hook; adding one
   touches `gecko-extension-api`, the assembler, and `build_host_bridge`. The CLAUDE.md wiring
   rule (build extensions only in the arms that use them) applies to registry construction.
7. **The static lint is red on arrival too.** The ledger says only the dynamic W5a test stays
   red until the cyber migration. `detect/mod.rs:133,186` contain literal
   `insert … isa technique-detection` / `alert-disposition` strings outside `mem/tql.rs`, so
   the static lint fails for the same reason. It also needs a stated scope for test sources,
   which legitimately contain raw belief-tier inserts.
